# RubbageChat 架构评估与优化路线

> 结论：RubbageChat 是经典的 **C/S（客户端/服务器）架构**，并且是
> 「服务端权威模型」——所有身份、会话、好友关系、消息顺序和附件授权
> 都只由服务端修改并持久化到 MongoDB，客户端只提交意图并渲染服务端
> 返回的快照。

## 1. 现状分层

```text
┌──────────────────────────┐
│  Windows 客户端 (Qt/QML) │   ChatController 是 QML 唯一入口
│  可靠发件箱 / 断线重发    │   隐藏连接、TLS、重连与状态快照
└────────────┬─────────────┘
             │ TCP/TLS + 长度前缀 JSON 帧 (ChatProtocol)
┌────────────▼─────────────┐
│  ChatServer (Qt/C++)      │   事件循环 / 限流 / 认证 / 在线状态
│  ChatCommandService       │   有界业务线程池隔离阻塞工作
└────────────┬─────────────┘
             │ mongocxx 驱动
┌────────────▼─────────────┐
│  MongoDB                  │   账号、会话、消息、好友关系
│  + 附件对象目录（磁盘）    │   附件正文不入库，仅存元数据+SHA-256
└──────────────────────────┘
```

判定依据：

- 客户端与服务端通过网络协议（TCP/TLS + JSON 帧）通信，职责边界清晰；
- 服务端持有全局权威状态（`seq` 序号、游标、回执），客户端离线后可从
  服务端同步恢复，符合 C/S 而不是纯 P2P 或本地优先架构；
- 数据库仅服务端可达（MongoDB 绑定本机地址），符合传统两层 C/S +
  持久化层的部署形态。

## 2. 已有优点

- 服务端权威模型：消息序号严格递增、同步游标、幂等 `clientMessageId`
  断线重发，天然支持多设备一致会话；
- 阻塞工作（MongoDB、PBKDF2）通过有界线程池隔离，TCP 事件循环不被卡住，
  并有 `maxPendingCommands` 过载保护；
- 附件对象目录与元数据分离，MongoDB 只保存授权元数据；
- 密码 PBKDF2-HMAC-SHA256、Token 摘要存储、TLS 1.2+、请求限流与连接限制
  等安全基线完整。

## 3. 改进与优化建议

### 3.1 短期（低风险，可立即做）

1. **附件传输升级**：目前文件以 Base64 单帧上传（约 6 MB 上限）。建议改为
   分块上传 + 断点续传 + 服务端合并，支持更大文件并降低内存峰值。
2. **离线推送**：桌面客户端无常驻进程时无法实时收消息。建议增加 WebSocket
   网关或 Windows 推送通知（toast），服务端事件 fan-out 与长连接解耦。
3. **可观测性**：为每个请求注入 `requestId`，结构化日志（JSON），暴露
   Prometheus 指标（连接数、队列深度、MongoDB 延迟分位数），便于定位问题。
4. **配置热加载**：限流阈值、注册开关、附件上限等改为可热更新，避免改
   配置即重启。
5. **全链路消息加密**：传输层已有 TLS，可在应用层增加可选的端到端加密
   （会话密钥协商 + 密文入库），服务端只存密文。

### 3.2 中期（架构演进）

6. **无状态网关 + 水平扩展**：把「会话在线状态」外置到 Redis，ChatServer
   可水平扩容；负载均衡层做 TCP/TLS 终结或 L4 转发，单机故障可迁移会话。
7. **事件总线**：在线推送从「遍历客户端连接」改为发布/订阅（Redis
   Pub/Sub 或 MQ），离线、多设备、未来 Web 端共用同一事件流。
8. **对象存储**：附件从本地磁盘迁移到 S3/OSS 兼容对象存储，客户端直传
   （预签名 URL）+ 服务端验权，减轻带宽与磁盘压力。
9. **读写分离 / 冷热分层**：历史消息按时间归档到独立集合或列存，常用会话
   热数据在内存缓存，控制 MongoDB 索引与磁盘规模。

### 3.3 长期

10. **服务拆分**：auth、message、presence、attachment 拆为独立服务（RPC
    或 gRPC），按需独立扩缩容；当前单体在功能稳定后迁移。
11. **实时音视频**：基于 WebRTC 增加语音/视频通话，信令复用现有通道，
    媒体走 P2P（ICE 打洞）或 SFU 转发。
12. **端到端加密默认开启**：服务端不可见明文，满足企业/隐私场景。
13. **多云与容灾**：MongoDB 副本集跨可用区、附件跨区域复制、一键灾备演练。

## 4. 结论

当前架构正确、安全基线扎实，适合先做「附件分块 + 可观测性 + 事件总线」
三项演进，再按需走向无状态化与微服务拆分，不必推倒重来。
